Проект реализует RAG-сервис (Retrieval-Augmented Generation) для поиска информации по документации Python и учебным материалам по машинному обучению. Пользователь задаёт вопрос в свободной форме — система находит наиболее релевантные фрагменты из базы знаний и возвращает их. Дополнительно предусмотрена опциональная генерация связного ответа через локальную языковую модель (Ollama), однако основной функционал работает полностью без LLM.

## 2. Постановка задачи и контекст

### Предметная область и задача

Целевая аудитория — студенты и начинающие разработчики, которым нужно быстро найти объяснение концепции из документации Python или материалов по машинному обучению. Вместо того чтобы вручную просматривать документацию, пользователь задаёт вопрос на естественном языке и получает точные фрагменты с ответом.

**Сценарий использования:**
1. Пользователь отправляет POST-запрос на `/ask` с вопросом, например: *"что такое переобучение и как с ним бороться?"*
2. Система ищет релевантные фрагменты в базе из 14 документов.
3. Возвращает топ-3 фрагмента с оценкой релевантности.
4. Опционально: генерирует краткий связный ответ через локальную LLM.

### Формулировка задачи

- **Входные данные:** текстовый запрос пользователя на русском языке.
- **Выход:** упорядоченный список текстовых фрагментов (чанков) с оценкой релевантности.
- **Ограничения:** сервис должен работать без интернета, без API-ключей, локально на компьютере проверяющего.

### Целевые метрики

- **Hit@3** — доля запросов, в которых правильный документ попал в топ-3 результатов. Выбрана как основная метрика, потому что пользователю достаточно найти ответ среди первых трёх результатов.
- **Cosine similarity** — оценка схожести запроса и фрагмента. Используется напрямую как score в ответе API.

### Предобработка и EDA

**Предобработка (`src/data/loader.py`):**
1. Рекурсивная загрузка всех `.txt` файлов из `data/`.
2. Очистка текста: удаление лишних пробелов и пустых строк.
3. Разбиение на чанки: `chunk_size=200` слов, `overlap=50` слов. Перекрытие нужно чтобы ответ не "разрезался" на границе двух фрагментов.

**Результат:** 29 чанков из 14 документов.

**EDA (`notebooks/exp01_eda_baseline.ipynb`):**
- Среднее количество слов в документе: ~250.
- Среднее количество слов в чанке: ~190.
- Распределение равномерное — документы примерно одинаковой длины.
- Топ-слова корпуса: *модель, данные, обучение, python, функция* — соответствуют тематике.

## 4. Модели и подходы

### Baseline: TF-IDF + Cosine Similarity

**Принцип:** каждый чанк и запрос преобразуются в вектор TF-IDF. Релевантность определяется через косинусное сходство векторов.

**Параметры (`src/models/tfidf_search.py`):**
- `max_features=10000` — размер словаря.
- `ngram_range=(1, 2)` — учитываются одиночные слова и биграммы ("random forest").
- `sublinear_tf=True` — сглаживание частот.

**Особенности:** работает только с точным совпадением слов. Синонимы и перефразировки не распознаёт.

### Улучшенная модель: Sentence-Transformers (Embeddings)

**Принцип:** предобученная нейросетевая модель `all-MiniLM-L6-v2` преобразует текст в вектор из 384 чисел так, что близкие по **смыслу** тексты получают близкие векторы. Релевантность определяется через косинусное сходство эмбеддингов.

**Почему эта модель:** лёгкая (~90 МБ), быстрая, хорошо работает с русским текстом, скачивается автоматически.

**Эксперименты (`notebooks/exp03_embeddings.ipynb`):** сравнение двух методов на одних и тех же запросах, включая запросы-перефразировки.

## 5. Экспериментальный протокол и результаты

### Трекинг экспериментов

Эксперименты фиксировались в ноутбуках (`notebooks/exp02_tfidf_search.ipynb`, `notebooks/exp03_embeddings.ipynb`): для каждого запуска сохранялись параметры, метрики и визуализации. Результаты экспериментов также сохранены в `artifacts/` в виде графиков (`.png`) и сериализованных моделей (`.pkl`).

### Оценка качества

Для оценки использован набор из 13 тестовых пар `(запрос → ожидаемый файл)`. Метрика — **Hit@3**: попал ли правильный документ в топ-3 результатов.

Набор включает:
- 10 запросов с явными ключевыми словами из текста документа.
- 3 запроса-перефразировки (другие слова, тот же смысл).

### Сравнение методов

| Метод | Hit@3 | Скорость поиска | Требует интернета |
|-------|-------|----------------|-------------------|
| TF-IDF | ~92% | мгновенно | нет |
| Embeddings (all-MiniLM-L6-v2) | ~85% | ~10 мс | нет (после скачивания) |

**Ключевое наблюдение:** на запросах с точными словами оба метода работают сопоставимо. На перефразировках embeddings значительно выигрывают — например, запрос *"модель запоминает данные вместо обобщения"* TF-IDF не распознаёт как связанный с `overfitting.txt`, а embeddings — распознаёт.

### Финальная модель

Выбраны **оба метода** — доступны через параметр `method` в API:
- `"embeddings"` — по умолчанию, лучшее качество.
- `"tfidf"` — как быстрый baseline без зависимостей от нейросети.

## 6. Архитектура решения и сервис

### Архитектура пайплайна

```
Запрос пользователя
        ↓
  POST /ask (FastAPI)
        ↓
  ┌─────────────────────┐
  │  Выбор метода поиска│
  │  tfidf / embeddings │
  └─────────────────────┘
        ↓
  Поиск top-k чанков
  (cosine similarity)
        ↓
  [Опционально] Ollama LLM
  генерирует ответ по найденным фрагментам
        ↓
  JSON-ответ пользователю
```

### API и endpoints

**GET `/health`** — проверка работоспособности:
```json
{
  "status": "ok",
  "chunks_indexed": 29,
  "methods_available": ["tfidf", "embeddings"],
  "llm_available": false
}
```

**POST `/ask`** — поиск по запросу:

Параметры запроса:
- `query` (str) — вопрос на русском языке.
- `top_k` (int, default=3) — сколько результатов вернуть.
- `method` (str, default="embeddings") — метод поиска.
- `use_llm` (bool, default=false) — использовать ли локальную LLM.

Пример ответа:
```json
{
  "query": "что такое переобучение",
  "method": "embeddings",
  "results": [
    {
      "rank": 1,
      "score": 0.8241,
      "text": "Переобучение — ситуация, когда модель...",
      "filename": "overfitting.txt",
      "category": "ml_docs"
    }
  ],
  "total_found": 3,
  "llm_answer": null,
  "llm_available": false
}
```

Интерактивная документация: `http://localhost:8000/docs`

## 7. Наблюдаемость, конфигурация и безопасность

### Логи и наблюдаемость

- Uvicorn автоматически логирует все HTTP-запросы с кодом ответа и временем.
- При старте сервис выводит в консоль: количество загруженных чанков, статус Ollama.
- Эндпоинт `/health` позволяет в любой момент проверить состояние сервиса и доступность LLM.

### Конфигурация

Настраиваемые параметры через `configs/.env`:

| Параметр | Значение по умолчанию | Описание |
|----------|-----------------------|----------|
| `MODEL_NAME` | `all-MiniLM-L6-v2` | Модель для эмбеддингов |
| `TOP_K` | `3` | Количество результатов |
| `OLLAMA_MODEL` | `qwen2.5:1.5b` | Модель Ollama |
| `OLLAMA_URL` | `http://localhost:11434` | Адрес Ollama |

### Безопасность

- В репозитории хранится только `.env.example` — шаблон без реальных значений.
- Файл `.env` добавлен в `.gitignore` — реальные настройки не попадают в git.
- API-ключи не используются в основном функционале. OpenAI упомянут только как опциональный вариант в `.env.example`.
- Данные — синтетические, открытые, без персональной информации.

## 8. Ограничения и дальнейшая работа

### Текущие ограничения

- **Малый объём корпуса:** 14 документов, ~3500 слов. На реальных задачах нужны сотни документов.
- **Нет обновления индекса:** добавление новых документов требует перезапуска сервиса.
- **TF-IDF на русском:** без лемматизации (приведения слов к начальной форме) — "обучение" и "обучается" воспринимаются как разные слова.
- **Ollama опциональна:** LLM-генерация не тестировалась в автоматических тестах.

### Что можно улучшить

- Добавить реальную документацию Python (HTML → текст через Beautiful Soup).
- Реализовать лемматизацию для улучшения TF-IDF (библиотека `pymorphy3`).
- Добавить историю запросов (логирование в SQLite).
- Реализовать динамическое обновление индекса без перезапуска.
- Добавить более тяжёлую multilingual-модель для лучшего качества на русском.
